# Fairy V3 Architecture

## Product boundary

Fairy V3 is a personal desktop AI with a complete project execution mode. It
is Windows-first with portable execution interfaces, and supports local and
cloud workers for one user across multiple devices.

The renderer is a consumer. It does not access project files, spawn commands,
select a preview, or mutate project state. The Core is the only authority for
Project, Conversation, Task, Version, Scope, Command, Changeset, Runtime,
Preview, Artifact, Checkpoint, and Memory state.

## Invariants

1. A Project is the long-lived work unit; a Conversation is an interaction
   scope, not the project state.
2. Every actionable request creates a Task before capability selection.
3. Every Task is bound to an immutable ScopeContract generated by the Core.
4. Every write is represented by a Changeset and applied to an isolated
   target Version.
5. Every command is appended to the durable ledger before worker dispatch.
6. Draft versions never become active without an explicit accept operation.
7. The renderer, Agent, and Companion cannot bypass the Command Bus.
8. Ambient Presence is separate from Work Presence. Companion code never
   invokes an LLM and never owns project or command state.
9. Internal reasoning is never represented as a user-visible event.
10. A missing sandbox disables run.sandboxed; it never falls back to a host
    shell.

## Components

### Desktop

The Tauri host supervises the local Core process, stores device credentials,
owns windows, and hosts the Rust local worker. React consumes a generated
CoreClient. Local application traffic uses private framed JSON-RPC; cloud
traffic uses HTTPS and resumable SSE through the same client interface.

### Core

The Python Core is a modular application with domain, application, ports, and
adapters boundaries. The domain and application layers do not depend on
FastAPI, SQLite, PostgreSQL, Tauri, S3, model providers, or operating-system
APIs.

### Workers

The Rust local worker handles scoped file and process operations. Generic
model-directed shell execution is available only through the dedicated WSL2
FairySandbox provider. The cloud worker executes in a non-root OCI sandbox.

### Storage and synchronization

SQLite stores local state and projections. PostgreSQL stores cloud state,
leases, ledger events, and the transactional outbox. S3-compatible storage
holds immutable version snapshots, artifacts, logs, and preview captures.
Devices synchronize domain events and version manifests by cursor; databases
are never mirrored.

An imported project is copied into Fairy-managed storage and initialized as an
internal Git repository. Each Task receives an isolated worktree. Accepting a
Version changes project.active_version_id with an optimistic project revision
check; it never silently overwrites the original imported directory.

## Permission model

Local permissions are device-global. Cloud permissions are configured
independently. Both support observe, standard, autonomous, and explicit
capability overrides.

- observe exposes read-only capabilities;
- standard requires policy approval for writes and execution;
- autonomous may auto-authorize configured low/medium-risk capabilities and
  may expose run.sandboxed when a healthy sandbox is available.

Scope enforcement, secret egress controls, sandbox requirements, and explicit
Active Version promotion cannot be disabled by a permission profile.

## User experience

Project mode uses a Task Timeline and Preview split view. A persistent context
bar displays Project, Conversation, Version, execution target, permission
profile, and synchronization status. Developer details are lazy-loaded in a
drawer. Functional scan lines, telemetry rails, and HUD motion communicate
real state and honor reduced-motion settings.
